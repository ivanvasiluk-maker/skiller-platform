## Правила каждого отчёта

По просьбе владельца каждый отчёт содержит: что сделано с прошлого отчёта; что делается сейчас; что не сделано/что мешает; конкретный следующий шаг; «Сделать руками Ивану» с понятными действиями либо «сейчас ничего». Пункты не объявлять выполненными без результата. Проверенный код, принятый сценарий, merge и публикация — разные состояния. Не выдавать количество тестов за процент готовности. Если нужен доступ, указывать конкретную систему/действие, не просить прислать секрет в чат.

Общий объём ещё большой: MVP не равен завершению всех трёх программ. Дальнейшая разработка сохраняет [общий список спринтов](SPRINT_ROADMAP_2026_10_31.md) и дополнение о тренировках. Новые идеи включаются в backlog с приоритетом; не вытесняют запуск MVP автоматически.

## Что делаем дальше до запуска

1. Проверить доступные настройки среды публикации и определить, какие из внешних гейтов можно подтвердить подключёнными инструментами без чтения клиентских записей. Неподтверждённое оставить открытым; не размножать формальные проверки вместо выполнения работы.
2. Подготовить и выполнить проверку настоящего backup в изолированной среде; подтвердить текущую production D1/ingress и отключение внешнего auto deploy. Не подменять её повторным тестом синтетической базы.
3. Организовать live-прогон синтетических диалогов выбранной моделью с согласованным API-доступом/бюджетом; передать точные ответы Ивану для экспертной приёмки. Не использовать реальные клиентские случаи.
4. Проверить приватный кандидат на реальном телефоне, ввод/голос, повторный вход, сохранение задач и честные ограничения напоминаний.
5. Утвердить актуальный оффер, доступ и порядок фактической оплаты/отказа/возврата. Не смешивать приложение с отдельным Telegram-ботом или выдавать ручное подтверждение заявки за работающую подписку.
6. Собрать реальные доказательства готовности для конкретного SHA, решить вопрос внешнего reminder-канала либо выпустить только честно обозначенные входящие. Затем — решение владельца о публикации, управляемый deploy и post-deploy проверка S08.

Read-only проверка доступных настроек выполнена 01.11; границы результата указаны в новой сцене. Настоящий backup/restore и внешние hooks ещё не подтверждены.

## Сделать руками Ивану

Сейчас можно подготовить, не меняя production:

- Выполнено 01.11: для live-проверки разрешён отдельный API-доступ и бюджет до $5. Секреты вводить через защищённую настройку, не отправлять в чат. Ассистент должен сначала уточнить, какой существующий доступ использовать, если это ещё не согласовано.
- Подтвердить именно для приложения: что продаём в первом запуске, цену/объём, как принимается реальная оплата и выдаётся доступ, правила отмены/возврата. Ранее названные цены бота/группы не переносить без проверки применимости.

Когда будет готов проверяемый приватный кандидат и точная ссылка:

- На своём Android пройти вход → ситуация → действие → сохранение/перезагрузка; проверить микрофон и сообщить конкретный сбой. Сейчас не отправлять проверять старую опубликованную версию вместо кандидата.
- Как психолог оценить предоставленные синтетические ответы: навык, безопасность, тон, отсутствие выдуманных фактов. Матрица и корпус готовы; точные live-ответы переданы в отчёте, экспертное решение ещё не получено.

Только если подключённые инструменты не дают нужных прав: ассистент назовёт конкретный экран настройки production/backup, необходимое действие и способ показать результат без секретов. Не перекладывать всю техническую приёмку на Ивана.

Финальное ручное действие — принять конкретный проверенный релиз перед публикацией. Сейчас такое подтверждение не запрашивается: необходимые проверки ещё не завершены.

## Короткий шаблон следующего отчёта

- Сделано: конкретный результат и доказательство.
- Сейчас: один активный этап.
- Осталось/мешает: только актуальные пункты.
- Сделать руками Ивану: действия сейчас либо «сейчас ничего»; будущие задачи помечать отдельно.
- Следующий шаг: конкретное действие ассистента и ожидаемый результат.
- Публикация: где находится изменение, изменён ли production.

# SKILLER — что принять владельцу перед публикацией

Дата: 26.10.2026. Эта ветка не опубликована в production. Реальные оплаты и сообщения участникам не отправлялись.

## Уже выбрано Иваном

- Первый оффер: группа СДВГ для взрослых.
- Проект срока хранения: 90 дней неактивности; автоматическое удаление не включается без утверждения политики.
- Для первого запуска — заявка и ручное согласование участия, без подписки и подключения платёжной системы.

## Пользовательский путь

1. Человек проходит онбординг и завершает практику.
2. После выполненной практики появляется «Узнать о группе СДВГ». В кризисном сценарии предложение не показывается; API также проверяет безопасность.
3. Участник отдельно оставляет Telegram/email и согласие на ответ. Имя и тексты диалогов в заявку не копируются.
4. Приложение показывает номер заявки и честное «оплата пока не подтверждена». Повторная отправка возвращает ту же активную заявку.
5. Иван открывает `/organizer`, раздел «Заявки на группу», и использует ключ организатора. Заявки не пересылаются автоматически в Telegram или почту.
6. Иван лично согласует программу, цену, расписание, места, оплату и условия отказа/возврата. Эти условия не подставлены из старой переписки и не выдуманы.
7. Только после проверки фактической оплаты Иван отмечает сумму и основание, подтверждает участие. На следующем открытии приложения участник видит подтверждение. Данные карты/банковские реквизиты в форму не вводятся. Форму нельзя использовать для автоматического списания.

До публикации нужны конкретные условия группы и выбранный способ реальной оплаты. В этой поставке не фиксировалась цена и не обещалось место без личного согласования.

## Настройки перед согласованным deploy

Ниже перечислены имена, реальные секреты в git не сохраняются. В текущем production ничего не менялось.

| Настройка | Назначение |
|---|---|
| `SKILLER_GROUP_OFFER_ENABLED=1` | Включить оффер после принятия условий. Без флага он скрыт и API не принимает заявки. |
| `GROUP_REQUESTS_ADMIN_SECRET` | Доступ владельца к заявкам и ручному подтверждению. По умолчанию доступ закрыт. |
| `PRIVACY_ADMIN_SECRET` | Отдельный доступ владельца к запросам удаления. По умолчанию закрыт. |
| `SKILLER_MAINTENANCE=1` | Приостановить продуктовые записи и HTTP-экспорт на время окончательной очистки. |

В локальных тестах используются только явно синтетические значения ключей, одноразовая D1 и выключенный AI. Для настоящего окружения нужны новые ключи, заданные после согласования места хранения.

## Удаление данных — ручной порядок

1. Пользователь в настройках вводит «УДАЛИТЬ». Сервер принимает идемпотентный запрос, выдаёт номер и блокирует новые записи в этот профиль. Браузер удаляет черновик текущего пользователя и гостевую cookie. На экране написано «запрос принят», а не «всё удалено».
2. Иван открывает `/organizer` → «Удаление данных». В списке есть номер и псевдоним, по которому проверяются копии аналитики.
3. До необратимой очистки включить обслуживание и остановить все cron/ручные экспортеры. Подождать завершения активных запросов (не менее 60 секунд после запроса; при известном активном задании — до его завершения). Одного отключения HTTP cron недостаточно, если вне приложения работает другой экспортер.
4. Проверить Google Sheets, если зеркало когда-либо использовалось: удалить строки псевдонима из USERS, EVENTS (user_id — колонка D), DAILY и FEEDBACK. Обновить агрегаты COHORTS. Проверить ручные выгрузки и доступные резервные копии. Если копий не было — зафиксировать их отсутствие. **Код не выдаёт ручную проверку зеркала за автоматическое удаление.**
5. Если поставщик не позволяет очистить управляемые резервные копии до истечения срока, не подтверждать полный процесс как завершённый. Дождаться истечения/очистки и отдельно согласовать с пользователем фактический срок. Не восстанавливать старую копию в рабочий контур без повторной проверки удаления.
6. После проверки отметить checkbox в форме окончательной очистки. API дополнительно требует режим обслуживания и возраст запроса. В рабочей D1 одной транзакцией удаляются профиль, сообщения, планы, цепочки, память, результаты, настройки, safety hold, заявки и контакт, idempotency cache, события и очередь под обоими идентификаторами.
7. При неизвестной новой таблице с user_id операция отказывает до удаления. При FK-ошибке транзакция откатывается. Другие пользователи и общий каталог навыков не удаляются.
8. В квитанции остаются случайный номер, статус и даты, без user_id и псевдонима. Персональный счётчик квоты также удаляется; общие суточные счётчики имеют срок действия 7 дней; просроченные строки очищаются при следующем запросе и не содержат исходного user ID или IP.
9. Сообщить пользователю результат по сохранённому номеру, затем вернуть обслуживание в обычный режим. Сообщение отправляет владелец вручную; приложение его не рассылает.

Это проверенный код удаления рабочей базы и проверяемая ручная процедура внешних копий; очистка настоящих внешних систем и backup в этой сессии не проводилась. Логически ошибочное подтверждение владельцем не может быть распознано автоматически.

## Срок 90 дней — проект политики

Предложение для закрытого пилота: после 90 дней неактивности начать ручную проверку удаления профиля, а не обещать уже работающий автоматический таймер. Неактивность нужно оценивать по последнему входу/взаимодействию, не по дате первого сообщения. Тексты согласия, сроки ответов на запросы, хранение backup и контакт оператора нужно окончательно утвердить до публичной рекламы. `/privacy` прямо сообщает, что окончательная политика ещё согласуется.

## Расходы AI

Реальные вызовы AI в этом цикле не выполнялись, ключ не использовался. Технические счётчики используют суточные хеши идентификатора/сетевого адреса. Это псевдонимизация, не доказательство полной анонимности; просроченные строки физически очищаются при последующем обращении. На сервере введены базовые суточные потолки: 30 потенциально AI-зависимых запросов на профиль, 120 на сетевой адрес, 500 на всё приложение. Счётчики атомарны в D1, превышение даёт 429. Обрабатываются message/situation/quickStop/confirmMemory, recommend/onboardingDraft и аудиорасшифровка. Превышение лимита не повторяет запрос к модели. Эти числа — технический стартовый предел, **не гарантия суммы в евро**: один запрос приложения может включать более одного обращения к модели.

До живого AI-теста Иван отдельно выбирает API-доступ и лимит расходов в евро; затем выполняется корпус из AI_ACCEPTANCE_CASES.md. Гостевые cookie не заменяют подтверждённый аккаунт. IP-ограничение само по себе не защищает от распределённого обхода, поэтому сохранён общий потолок. Полный нагрузочный аудит не проводился.

## Приёмка Иваном

- Проверить 10–15 отобранных диалогов после технического прогона корпуса; принять остальные только после исправления критических ошибок.
- На своём телефоне пройти один сценарий: ввод → голос/отказ микрофона → практика → результат → возврат → заявка. Настоящая запись и расшифровка требуют согласованного API-доступа.
- Принять политику, сроки хранения и условия группы.
- Отдельно разрешить deploy выбранной release-ветки и миграции 0018/0019. Публикация кода и draft PR не является разрешением deploy.

Свести цепочку S01–S07 и дополнение о тренировках в один reviewable PR в main. Проверенное основание main — `14a111fad823b6233b90f3217ce6fc37db3d5ca1`; до S08 текущая цепочка опережает его на 65 коммитов, не отстаёт, сравнение затрагивает 152 файла. Кандидат включает интеграцию диалога/портретов/историй миграций, hardening зависимостей и серверных границ, безопасный возврат после ухудшения, имена/доступный выбор тренеров, план дня, разовые входящие напоминания, проверки сети/конфликтов/реального срока, карту приёмки и актуальные спринты. Не реализованы полные ДБТ/РО-ДБТ, новый набор графических поз, кабинет психолога, подписка, игровые тренировки и доставка напоминаний в закрытом приложении. Они не выдаются за готовые функции.

Общий PR — альтернатива последовательному принятию цепочки, не разрешение объединять всё автоматически. Исходные PR остаются историей небольших проверяемых изменений. Окончательный release SHA определяется после всех необходимых изменений; текущие зелёные CI не переносятся автоматически на другой SHA.

## Проверка готовности и связь с SHA

Добавлена read-only команда `npm run release:check -- --release-evidence=PATH`. Файл оператора привязывается к точному HEAD и tree, чистому рабочему дереву и выбранному каналу напоминаний. Пример намеренно содержит pending и пустые поля: он должен отказывать.

Для каждого уже согласованного гейта требуются passed, ссылка/описание доказательства, проверяющий и дата с часовым поясом: CI, миграции/восстановление, браузер, настоящий production restore, binding/ingress, отключение внешнего автодеплоя, экспертная оценка живой модели, реальный телефон/голос, условия оффера/доступа, контроль расходов, откат и решение владельца о выпуске. При внешнем канале дополнительно проверяется externalReminderDelivery.

Проверка не делает эти действия сама, не проверяет удалённую ссылку и не превращает вручную заполненный файл в независимое доказательство. Оператор обязан сопоставить CI и все результаты с конкретным кандидатом. SHA публичного коммита может отличаться от локального служебного коммита при одинаковом tree: перед deploy нужен checkout именно выбранного публичного SHA.

Production deploy сохраняет требование ручного флага и запрет CI; теперь проверяет evidence до build/удалённых команд и повторно после build перед миграциями. Непринятый SHA, dirty source, отсутствующий файл или открытый гейт не запускают build/миграции/deploy. Это исполняемая часть прежних требований этапа 0 и приёмки, а не автоматическое подтверждение готовности.

## Процедура выпуска после закрытия гейтов

1. Принять точный кандидат с актуальным зелёным CI и всеми применимыми сценариями. Изменения после приёмки требуют нового SHA/проверки.
2. Проверить текущую production D1 и migration ledger, настоящий backup и восстановление в отдельную базу. Не создавать новую production базу взамен существующей.
3. Подтвердить доверенную авторизацию/ingress, отсутствие внешнего auto deploy, условия первого оффера, живую модель и телефон, расходы/наблюдение ошибок и план возврата.
4. В чистом checkout выбранного SHA создать внешний evidence-файл; read-only check должен пройти. Файл не содержит секретов или клиентских записей.
5. Только после решения о выпуске выполнить ручной deploy по [DEPLOY.md](../DEPLOY.md). Убедиться в применении 0020–0022 согласно фактической истории; старые миграции не переименовывать и не очищать ledger.
6. Post-deploy: новый/повторный вход, нужный тренер, короткий синтетический разбор, сохранение/повторное открытие дела и напоминания, экспорт, отсутствие доступа с другого аккаунта, состояние maintenance/оффера. Оценить ошибки и расходы.
7. При проблеме остановить продвижение/новые записи по плану, выключить новые функции подходящими флагами и вернуть утверждённую рабочую версию. Не откатывать данные удалением новых таблиц: сохранённые задачи/напоминания и исправления истории должны сохраниться. Совместимость старого кода со схемой проверяется до применения rollback; настоящий restore не заменять обещанием.
